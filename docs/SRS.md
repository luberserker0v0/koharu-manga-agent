# 軟體需求規格 (SRS) - MangaTranslationAgent

## 1. 簡介
### 1.1 目的
本文檔定義了 MangaTranslationAgent 系統的軟體需求，該系統用於自動化將日文/英文/韓文漫畫圖片翻譯並渲染為繁體中文。

### 1.2 範圍
本系統整合 Koharu HTTP API，提供從圖片上傳、翻譯管線執行、品質檢查、知識庫管理到結果匯出的完整工作流程。

### 1.3 目標讀者
- 開發人員
- 系統整合者
- 專案管理人員

## 2. 總體描述
### 2.1 產品視角
MangaTranslationAgent 是基於 opencode 平台構建的自動化代理系統，透過 Node.js 腳本與 Koharu HTTP API 互動。

### 2.2 使用者特徵
- 漫畫翻譯工作者
- 需要批量處理漫畫圖片的使用者
- 熟悉基本命令列操作的使用者

### 2.3 假設與依賴
- Koharu 服務已啟動並運行於 `http://127.0.0.1:9999`
- Node.js 已安裝且可在 PATH 中使用
- 翻譯所需的 LLM 模型已可用

## 3. 特定需求
### 3.1 功能需求
#### FR-01: 專案管理
- 系統應能列出所有可用的 Koharu 專案
- 系統應能開啟、關閉、創建專案
- 系統應能上傳圖片至當前專案（支援重複偵測）

#### FR-02: LLM 模型管理
- 系統應能檢查當前載入的 LLM 模型狀態
- 系統應能列出本地可用的 LLM 模型
- 系統應能載入/卸載 LLM 模型（優先以 provider/openai-compatible 模式，失敗後嘗試 local 模式）
- 系統應支援預設模型快取與自動載入

#### FR-03: 翻譯管線控制
- 系統應能選擇管線各步驟的引擎（偵測、OCR、翻譯、去字、渲染）
- 系統應能啟動翻譯管線並設定目標語言（zh-TW）
- 系統應能監聽管線進度並等待完成
- 系統應能處理管線錯誤與警告

#### FR-04: 品質檢查與修正
- 系統應能提取場景中的翻譯對照資料
- 系統應能使用 LLM 評估翻譯品質（語言正確性、風格一致性）
- 系統應能套用修正建議並觸發重新渲染
- 系統應支援知識庫注入以提升評估準確度

#### FR-05: 知識庫管理
- 系統應能從場景提取原文與翻譯對照
- 系統應能分析翻譯對照，提取術語、角色名、風格
- 系統應能批次更新知識庫
- 系統應能比對新舊翻譯一致性（自我反思）

#### FR-06: 匯出與輸出
- 系統應能匯出翻譯結果為 rendered/psd/khr 格式
- 系統應能將輸出儲存至 `translated/` 目錄

### 3.2 非功能需求
#### NFR-01: 效能
- 管線啟動後應在 600 秒內完成監聽
- 品質檢查應在 300 秒內完成
- 知識庫更新應在 300 秒內完成

#### NFR-02: 可靠性
- 系統應在 API 呼叫失敗時提供明確錯誤訊息
- 系統應支援 graceful shutdown
- Subagent 失敗不應導致主流程崩潰

#### NFR-03: 可維護性
- 所有腳本應遵循一致的錯誤處理模式
- 日誌應記錄至 `logs/` 目錄，支援依時間清理
- 配置應集中管理於 `.default-*` 檔案

#### NFR-04: 安全性
- 不儲存敏感資訊於程式碼中
- API 金鑰應透過環境變數或外部配置管理

### 3.3 介面需求
#### 3.3.1 使用者介面
- 命令列介面 (CLI)
- 透過 opencode 的 Question tool 進行互動選擇

#### 3.3.2 硬體介面
- 無特殊硬體需求

#### 3.3.3 軟體介面
- Koharu HTTP API (`http://127.0.0.1:9999/api/v1`)
- Node.js 執行環境

#### 3.3.4 通訊介面
- HTTP/HTTPS 協議
- SSE (Server-Sent Events) 用於即時進度監聽

## 4. 系統架構
### 4.1 高階架構
```
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   opencode      │───▶│  MangaTrans-    │───▶│   Koharu HTTP   │
│   Agent         │    │  lationAgent    │    │   API           │
└─────────────────┘    └─────────────────┘    └─────────────────┘
         │                       │                       │
         ▼                       ▼                       ▼
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   Subagents     │    │   Node.js       │    │   LLM Models    │
│   (pipeline,    │    │   Scripts       │    │   (Local/Remote)│
│   quality, kb)  │    └─────────────────┘    └─────────────────┘
└─────────────────┘
```

### 4.2 資料流程
1. 使用者啟動翻譯流程
2. 主 Agent 協調專案開啟、圖片上傳、模型載入
3. 啟動管線 → pipeline-runner subagent 監聽進度
4. 管線完成 → quality-checker subagent 評估品質
5. 若需修正 → 套用修正 → 重新渲染
6. 匯出結果 → 詢問是否更新知識庫
7. knowledge-builder subagent 批次更新知識庫
8. 關閉專案

### 3.4 測試需求
#### TR-01: 單元測試
- 配置系統（config.js）應有 100% 分支覆蓋率
- API 模組（api.js）應有 100% 陳述句覆蓋率
- 所有常數、端點、路徑應有對應測試

#### TR-02: 整合測試
- 所有 16 個腳本應能正確載入 shared 模組
- 無硬編碼 API URL 或路徑
- CLI 參數應能正確覆蓋配置

#### TR-03: 端到端測試
- 完整翻譯流程應能執行（需 Koharu 服務）
- 知識庫流程應能執行（需 Koharu 服務）
- 若服務未運行，測試應跳過而非失敗

#### TR-04: 覆蓋率目標
- 核心模組（config.js, api.js）覆蓋率 ≥ 95%
- 總測試數 ≥ 100 個
- 所有測試應在 1 秒內完成
